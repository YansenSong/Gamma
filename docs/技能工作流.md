# 自动测试评分应用构建技能工作流

本文说明 `autotesting-app-builder` 如何从三份业务材料生成离线 Windows 评分应用，以及每一步形成的文件、需要核对的内容和交付条件。具体执行约束以 [`SKILL.md`](../autotesting-app-builder/SKILL.md) 和技能的 [`references/`](../autotesting-app-builder/references/) 为准。

## 一、输入、输出与基本原则

一次构建需要三份属于**同一业务项目**的输入：

| 输入 | 用途 | 关键要求 |
| --- | --- | --- |
| 评分规程 PDF | 提供评分档位、条件、例外及计算依据 | 规则须能定位到具体页码和条款；表格、公式应核对页面图像。 |
| 评分 Excel | 定义实际需要计算的项目、输入单元格、分项分数及汇总分数 | 先盘点工作簿，再按其现有单元格寻找 PDF 规则。 |
| 检验报告 DOCX | 定义报告版式和自动填充位置 | 必须是带 `{{ }}` 标记的空白模板；已填好的报告不能替代模板。 |

仓库的 [`test-materials/`](../test-materials/) 仅是一组三文件测试输入。处理新项目时，应提供该项目自己的材料。源文件只读；公式写入生成项目中的工作簿副本，报告也从模板副本生成。

**得分由 Microsoft Excel 原生公式计算。** AI 根据材料编写并核验公式；Python 负责输入检查、在安全副本上规范化数据、调用 Excel 重算、读取结果、填充报告及记录审计，不另写一套 Python 评分算法。生成后的应用应能脱离本仓库离线运行，但目标 Windows 机器仍需有可用的 Microsoft Excel。

整体路径如下：

```text
建立环境与项目副本
  → 盘点 Excel 评分目标和实际填写方式
  → 对照 PDF 制定评分细则与规则记录
  → 暂存公式并用原生 Excel 验证
  → 映射 DOCX 填充位置
  → 固化项目配置并生成 Windows 应用
  → 用真实填写方式验收
  → 记录状态、打包与交付
```

## 二、建立环境和项目副本

技能目录本身只存放可复用的代码、模板和说明。工作环境和生成项目放在其外部。开始接触业务文件前，先阅读 [`references/environment.md`](../autotesting-app-builder/references/environment.md)，在技能的父目录创建 `.venv/`，安装 `requirements.txt`，再运行 `scripts/check_environment.py`。公式提交及最终验收需要 Windows 上的原生 Excel；环境预检未通过时，应先解决其报告的阻塞项。

随后使用 `scripts/init_project.py <pdf> <xlsx> <docx> --out <新项目目录> --name <项目名>` 建立独立项目。初始化会复制三份来源文件，生成分析清单和待审计划，并建立工作簿副本与应用骨架。典型项目位于 `generated_apps/<项目名>/`：

| 项目位置 | 作用 |
| --- | --- |
| `sources/` | 输入材料副本及来源追踪；原始文件不被改写。 |
| `analysis/` | PDF、Excel、DOCX 清单和核对证据。 |
| `review/` | 单元格、规则、公式和报告字段的计划及待决问题。 |
| `templates/` | 已填公式的评分工作簿及命名后的报告模板。 |
| `config/project.json` | 来源哈希、单元格映射、公式绑定、报告字段和运行配置。 |
| `src/`、`tests/`、`build.ps1` | 应用代码、项目测试及 Windows 打包入口。 |
| `dist/` | 构建后的可交付程序目录。 |

每个源文件及重要项目副本都应记录 SHA-256。项目初建时通常处于 `review_required`，不表示已能正式算分。

## 三、先读 Excel：确定评分范围和填写契约

Excel 是评分范围的起点。先只读盘点工作表、合并单元格、表头、行列标签、格式、数据验证、已有公式和手填区域。对每个评分目标，记录具体场景、输入单元格、得分率、分项分数、中间小计和总分，以及缺失的公式。完整目标集合写入 `review/rule-plan.json` 的 `scope.score_targets`；后续覆盖率以这个集合为准。

此时还要逐个确定**使用者真实会怎样填写**，形成输入契约。每个输入或同类输入组应说明：

- 接受哪些原始值、单位与等价写法，以及规范后的值；
- 空白、显式 `0`、否定答案、未发生、未测试各表示什么；
- 多列互斥、次数合计等跨单元格约束；
- 不合法或含糊输入如何按工作表和单元格报错；
- 使用者直接编辑评分表时，公式如何处理原始值；应用在副本中规范化后又如何处理。

例如，标题为“是否完全自动通过”的格子，应检查 `是`、`否`、`1`、`0` 等可能写法，并验证业务上等价的写法得分相同；不能只测试应用规范化后的 `1`。对次数类场景，要分清“发生了一次但落在零分档”“测试中没有遇到该场景”“本应测试却未完成”。完全空白的一行也可能与填了 `0` 的一行不同。各场景的含义须有材料依据；如果缺失会改变分数，就记录明确问题请用户决定，不能套用通用默认值。扣分项空白是否代表零次扣分，也按该项目的填写约定核对。

不要因为 PDF 多提了一种情况，就自动给 Excel 增加新列或新问题。先检查现有状态列、档位次数列（包括零分档）或已有衍生量能否表达。确实无法计算某个现有得分格时，记录缺少的事实和目标单元格；改变工作簿结构须另行得到用户授权。

## 四、再读 PDF：逐格建立规则与评分细则

对 Excel 中的每个得分目标，先写出公式必须回答的问题，再查找 PDF 中对应的条款、表格、前提和例外。文本抽取便于检索，但涉及公式、符号、合并表格或页码时，应核对 PDF 页面图像。记录页码和简短证据，并将规则与具体单元格绑定。PDF 中没有对应 Excel 得分目标的内容，可以记为范围外背景，不自动变成新评分项。

规则计划经 `scripts/publish_scoring_rules.py` 形成结构化的 `scoring_rules.json`、待决问题以及必要时的 `业务评审.md`。AI 可依据清楚的来源自行确认规则，并如实记录确认者为 AI；遇到会改变得分或报告含义、而材料无法确定的解释，先将问题和来源写入项目记录，再在对话中给用户列出互斥选项及影响。用户答复也要连同理由、时间和适用的来源哈希保存。不能为了继续构建而暗选一个分数。

随后按 Excel 的评分项目和目标格编写 `评分细则.md`，逐项说明输入、条件、档位、边界、例外和计算方式，并引用对应 PDF 依据。该文档不是 PDF 全文评分项的改写；`scripts/validate_scoring_spec.py` 可检查规则 ID、来源哈希和覆盖关系，但业务正确性仍需结合原始材料核对。

## 五、编写公式并通过原生 Excel 验证

对原表中没有公式的评分格，编制逐格公式计划：目标地址、依赖输入、规则 ID、预期边界结果、引用和风险。已有公式应保留，除非其修改已纳入明确的计划。用 `scripts/write_scoring_formulas.py prepare` 在暂存副本中检查语法、引用、循环和越界；通过后再用 Microsoft Excel 做原生重算。`commit` 阶段要求规则、评分细则和逐格确认一致，并在成功验证后建立唯一备份、写入项目工作簿副本及哈希回执。

验证不能只看一个选中的分数。应检查每个分项、小计和总分是否有 `#DIV/0!` 等 Excel 错误，特别覆盖：

1. 每类输入的实际原始写法及等价写法，例如 `是` 与 `1`；
2. 刚好处在档位边界的值，以及超出有效范围的值；
3. 整行零、整行空白、未用的互斥档、零分档发生一次；
4. 场景零次发生时的分母为零及业务规定的得分；
5. 直接在评分表输入与应用在副本中规范化输入两条路径的结果一致性。

如果 PDF 没规定某个会改变分数的状态（如应计分场景零次发生），应保留待决并请用户解释。`0` 不能自动当作“未填写”，也不能让合法业务数据得到 Excel 错误。用 `scripts/diff_workbooks.py` 核对仅计划中的单元格发生变化，并验证原始工作簿哈希不变。工作簿直接交给使用者填写时，其公式自身必须支持已确认的原始写法，不能依靠应用的预处理掩盖公式错误。

## 六、映射 DOCX 报告字段

只接受带 `{{ }}` 标记的空白报告模板。使用报告检查和位置导出脚本，盘点正文、表格、页眉、页脚以及被 Word 拆分的文本片段中的标记。每个无名位置要按上下文赋予字段名，并绑定已确认的 Excel 得分、原始输入或系统字段；标记集合须与 `report_output.fields` 完全一致。来源不明或同一位置存在多种合理含义时，记录问题并请用户确认。

命名操作写出新模板，不修改输入 DOCX。用代表性数据渲染后，检查所有应填位置、页面布局和有无残留标记。最终检验报告只能替换已映射的可填区域；静态文字、样式、页眉页脚、图片、签名区等其余内容和格式都应保持原样。工程状态、审核情况和来源信息写入独立审计记录或应用界面，不写入报告，也不额外加“非正式”标识。

## 七、生成应用并处理已填评分表

完成公式和报告映射后，用 `scripts/freeze_project.py` 固化项目配置。生成的应用以**上传已填 Excel 工作簿**为常规入口：先核对工作簿身份、公式和输入；按项目输入契约在安全副本上规范化必要的值；调用本机 Microsoft Excel 完整重算；读取公式结果并填充报告；最后保存报告、计算副本和审计记录。上传原件应保持字节和哈希不变。通用应用模板不认识具体项目的“是/否”、空白或零次规则，必须在生成项目中实现并验证这些契约。

审计信息应能追踪原始输入、规范化值、使用的规则、Excel 版本、计算副本哈希、报告字段来源和输出文件。工作簿公式被改动、必要结果缺失、输入无效或原生重算失败时，应用应阻止报告包输出，不能悄悄给出 Python 备用分数。

## 八、验收、状态与交付

使用至少两份内容不同的已填工作簿运行完整流程，并覆盖每类真实填写方式。核对两份报告中的分数均等于相应工作簿原生重算结果，差异与输入变化相符，上传原件哈希未变。再验证篡改公式、缺失结果和 Excel 重算失败时均会阻断输出。报告应检查未填标记、静态内容与版式；Windows 程序应从不依赖本仓库的独立目录启动。模拟重算测试可作工程证据，不能替代本机 Excel 验证。

项目状态要如实区分：`engineering_sample` 表示仍缺业务核对、真实数据或原生验收等必要证据；`business_validated` 只在规则、Excel 映射、报告映射、计算权威及实际验证均完成后使用。材料或配置变化会使相应的确认记录失效，需要重新验证。`scripts/write_manifest.py` 和 `scripts/verify_release.py` 用于记录和检查交付状态。

交付时最需要找到两个位置：

| 交付物 | 在生成项目中的位置 | 使用提示 |
| --- | --- | --- |
| Windows 程序 | `dist/<应用名>/<应用名>.exe` | 一并保留整个 `dist/<应用名>/` 目录。 |
| 已填公式评分表 | `config/project.json` 中 `excel_output.template` 指向的 `templates/*.xlsx` | 文件名以项目配置为准，不默认叫 `score.xlsx`。 |

生成项目还应包含自己的 `README.md`、交付清单、测试记录和审计文件，写明实际文件位置及已知限制。仓库中的 `generated_apps/` 和 `.venv/` 是本地输出，不属于技能源码或测试材料。

## 1. 需求来源与目标边界

### 1.1 用户原始需求的六个连续动作

**A. 输入**：提供三类文档：①评分规程 PDF，②评分 Excel 表格，③检验报告模板（以 `.docx` 为目标格式，需填处用 `{{}}`）。

**B. 解析规程**：AI 按 PDF 原文提取评分项目、输入指标、判定逻辑、边界阈值、加扣分、权重/封顶、例外、缺失值与取整规则等，生成可读、可追溯的 `评分细则.md`；不能只是粗略复制 PDF 全文。

**C. 公式改造**：根据评分细则和原始评分 Excel 的真实布局，准确找出每项测量/表现单元格与对应得分单元格，在得分格写入 Excel **原生公式**；保持原表结构和格式，提供允许人员填写的评分模板；公式和 PDF 来源可逐项复核。

**D. 报告映射**：扫描 Word 中每个 `{{}}`，根据上下文判断其代表的业务字段，把它映射到 Excel 的具体结果（尤其是得分单元格）；把匿名占位符命名并建立一份机器可读、可人工审查的映射表。

**E. 一次性构建**：打包成针对这套文件的 Windows 图形应用，连同带公式 Excel 模板和报告配置一起交付。

**F. 日常执行**：人工填写评分 Excel 中的试验表现，打开 EXE 上传**已填的整份 Excel**，程序读取其计算结果，填好 Word 报告并输出。原则上不重新询问已经在 Excel 填过的事实数据。

### 1.2 不属于本次强制范围的内容

- 不要求 EXE 在运行时调用大模型、云 API、RAG、网络 OCR 或在线数据库。
- 不要求将整个 AutoTesting 旧 IVISTA 平台迁移到 Gamma；旧业务平台不是运行时依赖。
- 不要求无来源地实现所有任意复杂的 PDF 自然语言评分条款。“无法可靠推导”必须以待审状态明确呈现，而不是生成猜测公式。
- 不要求默认支持 `.xls`、`.xlsm`、ODS、PDF 格式的报告模板、图片式填报、嵌入 VBA 宏等；若不支持，应早检测、清晰报错。
- 不要求在没有用户真实资料和审批的情况下生成“正式已验证”的业务评分报告。
- 默认最终报告为 Word `.docx`；如果增加 PDF 导出，作为可选增强，不能替代 Word 输出。

### 1.3 最重要的业务不变量

| 编号 | 不变量 | 任何违反都视为重大缺陷 |
|---|---|---|
| INV-01 | 交付 Excel 中每个已确认的自动评分格必须有经核验的 Excel 公式 | 不得只写固定数字或 Python 算分 |
| INV-02 | EXE 的日常默认输入就是用户上传的**完整 Excel** | 不能仅把它当成 JSON/事实提取来源 |
| INV-03 | Word 报告中的得分必须来自**本次上传 Excel 的相应单元格** | 不能来自内置空白模板、历史缓存或示例 |
| INV-04 | 重算应作用于用户工作簿的**安全副本**，不得悄悄改动用户上传的原文件 | 保护原件与溯源 |
| INV-05 | 公式校验基于关键公式/结构的基线，允许人工填写的事实格变化 | 不能用整个文件 hash 必须相等来验证上传件 |
| INV-06 | `{{}}` 必须全部得到明确的名称和来源，或作为阻断项暴露 | 不能遗漏或自动填空字符串掩盖失败 |
| INV-07 | 规则、公式、Excel 映射和报告映射都需来源与审核状态 | 不能由“测试通过”自动推导“业务认可” |
| INV-08 | Microsoft Excel 无法原生重算或重算失败时，不伪造结果 | 不能用 openpyxl 当计算引擎 |
| INV-09 | EXE 离线运行时不依赖 Gamma/AutoTesting 源码和 AI 服务 | 交付物要封装完整 |
| INV-10 | 工程测试、业务确认、正式交付是三种不同状态 | 不可以 mock 测试作为真实验收证据 |

### 2.4 已识别的技术断点（重点核查，不准漏）

**断点 A：上传 Excel 路线不对。** 先前静态检查发现：

```python
# assets/windows-app-template/src/main.py 中的旧思路
read_facts(path, spec)
run_job_from_facts(...)

# src/app_service.py 中的旧思路
load_facts_from_excel(path, spec)  # 只提取映射事实
shutil.copy2(workbook_template, xlsx)  # 重建一份内置模板副本
_excel_native_recalculate(xlsx, input_values)
```

这与“以用户已填写完整 Excel 为唯一得分来源”不一致。**必须添加独立 `run_job_from_workbook()` 并设为上传 Excel 的主入口**。既有 `run_job_from_facts()` 可用于旧模式或表单模式，但不能偷换新流程。

**断点 B：PDF 解析不是评分细则 MD 生成。** 当前 `inspect_pdf.py` 保存的是结构化 JSON，需要明确的规则综合、审查、MD/JSON 输出与测试；不要只在 `SKILL.md` 中写一句“请 AI 生成”。

**断点 C：公式写入器接收的是现成计划。** `write_scoring_formulas.py` 负责校验与写回，但不负责自动理解 PDF 或决定“试验表现单元格→得分单元格”对应关系；应补一条从分析、候选计划、人工审查到公式写入的正式链路。

**断点 D：当前公式目标往往只接受空白且已存在 XML 节点的格子。** 需要验证未格式化空白格、已有手工分数字面值、合并单元格、既有公式等情况；不允许未经批准覆盖已有业务内容。

**断点 E：`scoring.inputs` 非空约束可能妨碍“完全读取上传 Excel”模式。** 检查 `project_validation.py`、`main.py` 中的字段表单构造与运行时校验；按模式区别要求，不要靠添加虚假输入绕过。

**断点 F：原测试部分使用 mock Excel。** `test_three_document_flow.py` 中的 `TEST_DOUBLE_ONLY` 不是 Microsoft Excel 真正执行；`test_generated_application.py` 的示例缺失时会 skip，不能把“有测试文件”当作真实业务闭环通过。

**断点 G：分发文件与软件依赖。** 现有 PyInstaller 是 onedir，运行时 Excel COM 依赖本机 Microsoft Excel；要在交付清单和 UI 内真实注明。

## 3. 产品架构：必须拆成两个严格分离的阶段

```text
┌────────────────────── 一次性 Skill 构建阶段（AI + 人工确认） ──────────────────────┐
│ ① 评分规程 PDF    ② 原始评分 Excel    ③ 标有 {{}} 的 Word 模板                 │
│         │                  │                    │                            │
```

### 3.1 为什么必须分阶段

- AI 理解评分规程具有一定语义不确定性，应在**构建阶段**审阅与冻结。
- 日常评分和填报应是**确定性的文件处理**，不依赖模型随机性。
- 对同一 Excel 与已冻结版本映射，日常结果应该可复现；改变规则必须重新生成版本并重新审查。
- 阶段间接口应是**版本化项目配置 + 公式评分模板 + Word 模板 + 可验证哈希及人工决策**，不能是仅存在某轮聊天里的自然语言解释。

### 3.2 构建状态模型（不可混用）

建议最少区分：

1. `analysis_complete`：三份文档已盘点，但不代表规则已确认。
2. `review_required`：存在评分细则、Excel 单元格或报告字段待确认。
3. `engineering_sample`：技术链路可跑，仍缺正式业务确认或真实证据。
4. `business_validated`：业务规则、公式/Excel 映射、报告映射、计算权威都有具体审批和真实测试证据。
5. `release_blocked`：构建或正式交付因未满足强制门禁阻断，输出可包含待审包/非正式预览，但不得冒充正式报告。

允许内部实现沿用现有 `release_status`、`validation_state` 并扩展。**不要把 `analysis_complete` 当成 `business_validated`**。

## 4. 构建阶段详细实现要求

### 4.1 S0：初始化、环境和源文件盘点

2. 只读盘点原始文件，分别记录路径（仅开发环境可见）、角色、格式、字节数、SHA-256、文档版本或元数据。
3. 原件**默认不可覆写**；在独立项目输出目录生成新带公式模板。若兼容现有 `write_scoring_formulas.py commit` 的原路径写回，必须是单独明确授权的可选模式，且有唯一备份、hash 校验和失败回滚。
4. 独立生成工作区，例如 `<Gamma 的上级工作区>/generated_apps/<project-id>/`，不能把业务产物放入要求可复制的 `autotesting-app-builder` Skill 本体内。

```text
  analysis/
```

### 4.2 S1：PDF 规程解析 → 评分细则.md + 结构化规则

**不能只抽出页面文字。** 至少分两个动作：①确定性抽取，②AI 对规则进行语义归纳及核对。

**解析要求：**

- 提取标题、章节编号、项目编号、段落、表格、注释、脚注、可能的跨页表格；尽可能保留 PDF 页码和文本块/表格坐标或稳定 SourceRef。
- 检测表格续页、阈值单位、边界比较符号、权重、封顶/保底、扣分项、优先级、例外情景、四舍五入规则、测试是否有效等。
- 识别纯图片/扫描页、抽取结果过少/乱码/公式数学符号缺失情况；如果 OCR 未实现，应输出**明确阻断**而不是沉默使用缺失文本。
- 识别“评分总则/满分/分项得分/组合得分/权重”与一般描述性文字，不强迫所有段落生成公式。
- 分清试验事实输入、人工判定输入、可计算的评分规则和上下文说明。
- 每条规则都应有来源与置信/审核状态，不能凭常识补写章程没有的阈值。

**强制交付两个互补文件：**

`analysis/评分细则.md`：给业务人员阅读，逐项写明标题、适用条件、输入字段、单位、计算步骤、阈值、上下限、缺失处理、原文证据、待确认事项和拟映射的 Excel 输出格。

`analysis/scoring_rules.json`：给后续程序使用的结构化规则候选；**它不是运行时 Python 评分器**。例如：

```json
{
  "schema_version": "gamma-scoring-rules-v1",
  "source_pdf_sha256": "<实际SHA256>",
  "rules": [
    {
      "rule_id": "parking_time_score",
      "title": "泊车用时得分（仅示意）",
      "source_refs": [{"page": 12, "location": "表 4-1 第 2 行"}],
      "inputs": [{"field_id": "parking_seconds", "unit": "s", "type": "number"}],
      "business_logic": "此处应放实际 PDF 中经确认的规则，不能用示例代替",
      "thresholds": [],
      "missing_value_policy": "pending_review",
      "review_status": "pending",
      "issues": ["确认是否包含等号边界"]
    }
  ]
}
```

**上述字段、页码及例子仅为结构示例，不能当作真实 IVISTA 业务规则。**

MD 最好包含固定目录：

```markdown
# 评分细则（待审 / 已审核）
## 1. 文档身份与版本
## 2. 评分项目总览
## 3. 分项评分细则（逐条、逐页证据）
## 4. 输入指标字典（含单位和允许范围）
## 5. 汇总及等级规则
## 6. 缺测、无效试验与人工判定
## 7. 未解析条款和歧义清单
## 8. Excel 映射与公式编写准备
## 9. 审核记录
```

**验收**：任取一条可评分规则，应能从 MD/JSON 找到 PDF 的具体来源；任取一个最终写入的公式，应能反向追溯到规则 ID 和 PDF 来源。扫描/乱码页必须被指出。若重要评分章节未覆盖，明确 `not_covered`；不要通过写“全部覆盖”掩盖不足。

**复用建议**：优先阅读 AutoTesting 的 `charter/markdown_service.py`。如果直接移植牵涉旧 Python 评分服务或大量运行时依赖，优先在 Gamma 内实现轻量的规则文档生成层，只共享纯解析/文档渲染结构。

### 4.3 S2：Excel 结构扫描和语义定位

**目标**：不是找到“有得分二字的格子”就写公式，而是可靠识别“测量表现/人工判断格”和“公式得分格”之间的具体关系。

对每个工作表和候选区域，至少分析：

- 表名、表是否隐藏、各区域标题、合并单元格、行列标签、打印区域、有效区域。
- 表格中输入值、输入类型、单位及数据验证（数字/是/否/等级/日期/空缺）。
- 已有公式、公式引用关系、汇总公式和单独的分项得分格。
- 样式、保护、命名区域、跨表引用、隐藏行列、条件格式、图表、外部链接、数据透视及其他可能影响编辑保真度的功能。
- 对规则与单元格建立**候选集合**；同名标签、重复项目、多个试验次数、多种评分策略的场景不能自动拍板。

建议结构化输出：

```json
{
  "schema_version": "gamma-workbook-mapping-v1",
  "source_workbook_sha256": "<实际SHA256>",
  "items": [
    {
      "rule_id": "parking_time_score",
      "input_cells": [{"sheet": "评分明细", "cell": "D15", "meaning": "泊车用时", "unit": "s"}],
      "score_cell": {"sheet": "评分明细", "cell": "F15"},
      "existing_value_kind": "blank",
      "mapping_status": "proposed",
      "candidate_evidence": ["左侧项目名称", "表头单位", "PDF评分项目编号"],
      "review_question": "确认 F15 是该项最终得分而不是最高分栏"
    }
  ]
}
```

以上表名与地址都是虚构示例，必须由本地文档实际检查得出。

**语义审核原则：**

1. 同一个规则映射多个得分格，或多个规则合到一个得分格，应明确区分关系：`one_to_one`、`one_to_many`、`many_to_one`、`many_to_many`、`unmatched`；必须记录理由。
2. 同名项目出现在不同页/不同场景，不能只凭字符串相似度合并。
3. 对已含正确公式的格子保持原公式并验证，不重复覆盖；对没有公式但已有手工数字的格子只能通过明确批准的替换方案编辑。
4. 区分“原始表现数据为 0”“合法得分为 0”“尚未填写”“试验不适用”“公式结果为空/错误”，不得合并为单一状态。
5. 用户已有的 Excel 数据验证、下拉框、格式、合并区域、页眉页脚/打印设置等应尽可能保留；检测到不支持修改保真的功能时阻断写入或要求人工选择兼容路线。

### 4.4 S3：规则 → Excel 公式计划 → 原生边界校验 → 带公式模板

**目标**：Skill 输出的是普通 Excel 软件能够自己算分的 `.xlsx`，而不是 Excel 显示分数、实际上由 Python 写入固定值。

建议每个目标公式计划记录：

```json
{
  "sheet": "评分明细",
  "cell": "F15",
  "original": null,
  "formula": "=IF(D15=\"\",\"\",IF(D15<=10,2,0))",
  "inputs": ["评分明细!D15"],
  "rule_ids": ["parking_time_score"],
  "pdf_refs": [{"page": 12, "location": "评分表某一行"}],
  "rule_explanation": "示意公式；实际逻辑必须来自 PDF",
  "boundary_checks": [9.999, 10, 10.001],
  "missing_value_policy": "empty_not_zero",
  "rounding_policy": "none",
  "risks": [],
  "review_status": "approved"
}
```

**重要：示例中 `10` 和 `2` 不代表任何真实评分规程，不能复制成产品业务逻辑。**

强制要求：

1. 公式必须使用 Excel 原生规范的函数与引用；写入 OOXML 时注意公式语言与分隔符规范，不能直接写中文函数名或随意转换地区小数符号。
2. 必须正确处理阈值边界 `> / >= / < / <=`、小数精度、封顶、扣分限额、试验次数、条件组合、权重、取整与例外。**不允许因为示例测试只覆盖两个数字就认定公式正确。**
3. 对无数据的输入区分“未录入”与“真实零值”。若章程规定无数据不得得分，则空值必须产生明确可验证的缺失状态，不能默认 0 分。
4. “主观人工判定”应在 Excel 留出可录入/勾选的字段，再由 Excel 公式根据规则转换成分数；AI 不得伪造人工判断。
5. 如果 Excel 公式无法忠实表达已确认条款，记录 `manual_action_required` 或待审处理方式，不要输出貌似正常的公式。
6. 在写回前检测目标位置是否受保护、是否合并区域非左上角、是否已有公式、是否是带值单元格；每个覆盖动作都必须经过审查。特殊格式的目标先形成副本测试。
7. 优先**默认写出新的** `approved/scoring_template_with_formulas.xlsx`，保留原始文件不可变；如沿用现有“备份后覆写原路径”，应有清晰选项，不应静默覆盖用户源数据。
8. 继续使用现有 `write_scoring_formulas.py prepare/commit`、哈希、差异检验与 `validate_formula_stage.ps1` 的架构；对 XML 中完全没有 `<c>` 节点的合法空白格及已有手工值需要设计兼容策略，并加测试。
9. 边界期望值应来自**经业务核对的规程解释或人工确认的固定测试样例**，不能通过重用待测公式或同一个 AI 公式计算器产生“期望结果”，否则属于同源自证。
10. 原生 Excel 验证是硬门禁：在隔离副本上写样例输入，`CalculateFullRebuild()`（或明确等效的完整重算）、保存、关闭、重新读取，比较实际缓存结果与独立期望值；保存 Excel 版本、输入/输出和证据文件哈希。
11. 只有真正通过且审核完成的公式才能标记 `approved`；不完整项目可以输出工程预览/待审工作簿，但不能把所有单元格标记为最终可用。

**建议针对单元格的完整测试集合**：阈值下方、阈值点、阈值上方、零、负数（若不合法须拒绝）、极值、空白、文本、无效枚举、多个输入组合、跨表引用、封顶前后、四舍五入临界、总分一致性。

### 4.5 S4：匿名 `{{}}` → 具体 Excel 字段映射

**输入**：用户原始标注版 Word 模板。**输出**：具名 Word 模板、全字段映射清单、审核问题与版式验证。

**支持的基线**：`.docx`，格式如 `{{}}`、`{{ }}`；用户可以在同一份 Word 中多次写匿名标记，并使用表格、正文、页眉页脚。标记在 Word 内部 XML 中可能拆分为多个 run，必须跨 run 识别。

每一个标记必须记录：

- `position_id`：稳定位置标识，不只是第 N 个；含 part、段落/表格/页眉页脚、相对上下文和源文档哈希。
- `context`：标记左右文案、所在表格行/列标题（若可安全读取）。
- `field_id`：赋予唯一语义名称，例如 `parking_safety_score`。
- `source`：具体哪张 Excel 表、哪个**公式得分格**，或其他已声明、可追溯的元数据来源。
- `value_type`、展示精度、单位、空值策略、是否影响正式结论。
- `confidence` / `review_status` / `reviewer` / `evidence` / `question`。

**推荐将机器配置拆分为“Word 位置→字段 ID”“字段 ID→Excel 结果 ID”“结果 ID→具体工作簿坐标”三个层次**；项目中现有 `report_output.fields` 可以继续作为中间层，不必为概念上的优雅破坏兼容性。

示意：

```json
{
  "report_positions": [
    {
      "position_id": "word/document.xml:p[18]@22",
      "context": "智能泊车综合得分：{{}} 分",
      "field_id": "parking_total_score",
      "source": {"kind": "score", "id": "score.parking_total"},
      "review_status": "approved"
    }
  ],
  "score_outputs": {
    "score.parking_total": {"sheet": "汇总", "cell": "F20", "value_type": "number"}
  }
}
```

这只是数据结构示意。实际 Word 的 `position_id` 取值要由扫描器生成，实际 Excel 坐标不得想当然。

**特殊情况：**

- 多个 Word 位置可以映射同一个 Excel 得分；必须允许复用字段或重复具名引用。
- 同一个 Word `{{}}` 需要两个得分合成显示时，优先在 Excel 设置一个明确的汇总公式格，并由报告映射指向该格；**不得在 Python 把两项分数合算成新得分**。
- 有些标记是车型、试验日期、样车信息或文本结论而非得分。要么从已声明的 Excel 元数据格读取，要么按确认方案用独立的可见输入字段；**不能把得分推断成“试验通过”“未碰撞”等缺失事实**。
- 若同一个标记代表无法从工作簿取得的业务事实，必须形成待审问题并阻断正式交付；不能直接填写“通过”“否”或历史内容。
- Word 中存在 `{{ name }}` 已命名标记时，验证其语义与配置一致；无名和已命名的混合要有确定性的处理规则。
- `{{}}`、`{{ }}` 要替换为具名简单表达式；不接受未经审查的 Jinja 复杂语法、循环、条件或模板中执行代码。
- 未标注为 `{{}}` 的 Word 普通文字、表格、图片、签名区域、页码、表头和样式默认**不得更改**。

**验证要求**：

1. `original_markers == mapped_positions`，每个位置恰好一个解释；一个 `field_id` 的所有使用点对应同一业务含义。
2. 生成**新**的已命名 DOCX 副本，不修改用户原始模板。
3. 用固定值做 Word 渲染，重新打开并检查正文、表格、页眉页脚和拆分 Run 的替换效果。
4. 对关键模板进行**视觉分页检查**：页眉页脚、表格宽度、分页符、字体、图片、签名块等是否异常；结构检查通过不等于版式一定正确。
5. 最终报告不存在任何未替换的 `{{...}}` 和异常空白关键字段。

### 4.6 S5：生成并冻结具体项目配置

构建产物必须将三份文件真正关联在一起。建议明确区分：

- **原始文档哈希**：规程 PDF、原始评分 Excel、匿名标记 Word 模板。
- **交付模板哈希**：改造后的带公式 Excel、已命名 Word 模板。
- **公式绑定**：分数 ID→工作表/单元格→精确公式→PDF 规则 ID。
- **上传件兼容性契约**：哪些表、得分公式、单元格地址、命名区域/必要结构不可变；哪些试验输入格允许用户填写。
- **报告字段契约**：Word 字段 ID→Excel 得分 ID/可审查的元数据来源→展示格式。
- **业务决策和审批**：内容绑定、时点、审批人、依据、未解决问题。
- **运行模式**：必须显式是 `uploaded_workbook`（或等价稳定名称），而不是隐式沿用原 `input_facts`。

## 5. 日常 EXE 模式：这部分必须真正落地（最高优先级）

### 5.1 正确的新调用链

建议在 `assets/windows-app-template/src/app_service.py` 暴露一个新的主入口：

```python
from pathlib import Path

def run_job_from_workbook(
    uploaded_workbook: Path,
    output_dir: Path,
    *,
    spec: dict | None = None,
) -> dict:
    """读取用户已填写的评分 Excel，生成对应的 Word 检验报告。

    得分只来自本次上传工作簿中已经审核、并经 Microsoft Excel 重算的公式格。
    禁止用 Python 再实现评分规则，也禁止把上传件数据复制到内置空白模板后冒充原件结果。
    """
    # 1. 校验配置与上传件身份/结构/关键公式
    # 2. 在输出工作区创建上传件的安全副本
    # 3. 通过 Microsoft Excel COM 原生重算安全副本，保存、关闭
    # 4. 用 data_only=True 重新打开该安全副本，读取已声明得分格
    # 5. 对得分的缺失、类型、有限性、Excel 错误码和审核状态进行校验
    # 6. 从已映射工作簿格读取必要的报告元数据（不得凭得分猜测事实）
    # 7. docxtpl 渲染具名 DOCX 副本，严格校验未解析标记
    # 8. 生成运行审计 JSON，原子发布最终文件包
    # 9. 异常则清理临时目录，保留用户上传原件
    raise NotImplementedError  # Codex 应将本示例替换为真正实现
```

**此处是接口设计示例，不应把 `NotImplementedError` 留在最终代码。**

`main.py` 应把选择文件/拖放的 `.xlsx` 分支接到：

```python
run_job_from_workbook(uploaded_path, output_dir)
```

而非当前的：

```python
run_job_from_facts(load_facts_from_excel(uploaded_path), output_dir)
```

允许原 `JSON / 表单录入 → 内置模板重算` 路线存在，但它必须有单独入口和标签，且不能默认为用户当前目标行为。如果该旧路线难以维护，可安全标注为 legacy 并在新模式中关闭，保留对应兼容测试。

### 5.2 上传 Excel 的验证方法不能照搬“源文件整体 hash 相等”

原因：用户只要填写了测评数据，上传 Excel 的 SHA-256 就必然与交付时的空白评分模板不同。

**正确做法是结构 + 关键公式 + 允许变更区域的分层验证**：

1. 校验文件真实为合法 `.xlsx`，大小/解压内容/是否加密/是否包含危险或不支持部件。
2. 校验项目版本/工作簿身份（可通过受控的隐藏标识单元格、受控定义名称、嵌入自定义属性或综合结构指纹）；不能只靠文件名。
3. 校验所需工作表存在，名称及关键坐标匹配；对有必要的命名区域、合并结构和核心汇总区域进行验证。
4. 校验**所有正式评分关键单元格中的原生公式**与冻结的 `formula_bindings` 匹配，至少覆盖所有最终报告使用的得分格及其关键公式依赖链；如仅校验输出格，必须明确非输出中间公式被篡改的风险并补充分层校验。
5. 人工测评输入格允许变化；已有试验数据不得被重新置零或替换成内置样例值。
6. 工作表允许用户实际填值造成的“文件不同”，而不是因为 hash 不同拒绝。
7. 若发现公式变成数值、公式被改、目标工作表被改名、映射格丢失、关键结构漂移，则拒绝正式报告并给出定位，例如 `评分明细!F15 应为公式，当前为常量`。
8. 如果用户人为修改了**非关键**格式但结构/公式仍兼容，应按清晰策略处理：要么允许并记录差异，要么说明为何不允许；不能以所有工作簿必须字节一致作为默认策略。
9. 处理公式字符串的等价性要谨慎：默认可先采取严格文本匹配（更易审计），若想接受 `$A$1` 等等价改写，必须有额外验证，不能用简单 `.replace()` 放行潜在差异。

建议将“交付模板版本身份 + 公式指纹 + 结构指纹 + 原始上传文件 hash”分别记录。

### 5.3 Excel 原生重新计算（作用于上传件副本）

修改 `scripts/recalculate_excel.ps1` 或新增 `recalculate_uploaded_workbook.ps1`，实现：

- 使用 `powershell.exe` + Excel COM，仅在 Windows 上运行；打开的是**经复制的用户上传工作簿**。
- 关闭 Excel 可见界面、更新外部链接、危险宏自动运行等风险；检查 `.xlsx` 与不支持的嵌入内容。尽可能使用 `AutomationSecurity=3`，关闭链接更新且不要忽略安全异常。
- 不向工作簿写入新的业务试验值；运行时处理“已填写 Excel”的模式只执行完整重算、保存、关闭，不应用 JSON payload 覆盖任何输入格。
- 正确管理 Excel 生命周期与异常：文件被占用、Excel 实例创建失败、打开失败、保存失败、重算超时/错误都应给出可理解信息，并终止正式输出。
- 保留 `Excel.Version`、是否完整重算、工作簿重算后 hash、时间戳、退出码/日志；尽可能排除异步查询/链接加载不确定性。
- Python 使用 `openpyxl.load_workbook(path, data_only=True)` 只是**读取 Excel 已保存的结果缓存**，不是计算公式；读取之前必须有原生完整重算成功证据。
- 不因 Excel 返回 `None`、`#VALUE!`、`#REF!`、`#DIV/0!`、`#N/A` 等而自动替换 0 或上次分数。
- 要防止并发任务争用同一 Excel COM 实例；先确保串行可复现，之后可做安全的多任务队列。

### 5.4 读取哪些格，如何处理数值展示

根据已确认配置读取所有 `excel_output.output_cells`，加上 Word 用到的其他明确信息来源：

```text
score_id     = score.parking_total
sheet/cell   = 汇总!F20
value_type   = number
value        = [本次上传Excel经原生重算后的实际缓存]
report_field = parking_total_score
```

**区分计算值与报告展示值**：Excel 中 `0.85` 可能展示为 `85%`，Excel 中 `92.50` 可能应在报告写成 `92.5`；这属于**格式化**而不是再次评分。可在配置中声明 `decimal_places`、`percent_display`、`unit_suffix`、`date_format`、是否要求保留尾零等；不得私自改变原评分数值或不知何处地四舍五入。

可以为报告提供字符串格式化工具，但应当对数值/百分比/文本/日期分别测试，并保留原始数值到审计记录。Word 中已经带单位（例如 `{{}} 分`）时，避免重复输出 `分分`。

### 5.5 Word 渲染与原子化交付

推荐输出命名：

```text
outputs/
  <项目ID>-<时间或运行UUID>/
    检验报告.docx
    评分工作簿_已验证副本.xlsx     # 推荐保留，便于复核；可配置是否向用户展示
    audit.json
```

要求：

1. 在临时工作目录渲染；Excel、Word 和审计三者都成功后，再一次性发布整组文件，不允许出现“Word 已存在但填一半”的正式输出。
2. 审计记录包含：原始上传路径或文件名（不泄漏多余隐私）、原始上传 SHA-256、重算副本 SHA-256、项目版本、关键公式校验结果、Excel 原生版本、读取的每个得分 ID/值/来源坐标、Word 字段解析情况、生成报告哈希与时间戳。
3. 输出 Word 必须可以被重新打开，全部目标标记正确替换；如模板具有用户特别要求的复杂表格/分页，需复核版式。
4. 可保留用户上传原件的副本或最终重算的工作簿，但任何操作都不应悄悄覆写用户的输入文件。
5. 报错时清理临时目录（保留必要的安全审计/脱敏错误日志）；不要输出易被误用的正式报告。

- `ScoreReader`：按确认的公式输出绑定读取得分缓存，检查错误和类型。
- `ReportContextBuilder`：字段映射和展示格式化；不能实施评分运算。

- `DesktopMainWindow`：文件选择、进度、结果展示；不应该拥有业务分数判断逻辑。

这可分别实现为函数、类或独立模块；遵循现有代码风格，但要保证能够单元测试。

### 6.3 错误分类建议

明确可恢复/不可恢复的失败类型：

| 错误类别 | 例子 | 应对 |
|---|---|---|
| `InvalidInputFile` | 不是 `.xlsx`、损坏、过大 | 阻断并提示重新选择 |
| `WorkbookVersionMismatch` | 工作表改名、项目身份不匹配 | 阻断，提示使用配套模板 |
| `FormulaTampered` | 得分格变为常量、公式内容改变 | 阻断，显示工作表!单元格 |
| `MissingRawObservation` | 必填的试验表现没有填写 | 阻断或按**已审核**缺失策略处理 |
| `ExcelUnavailable` | 本机未安装 Excel/COM 未注册 | 阻断，说明环境要求 |
| `ExcelRecalculationFailed` | COM 打开、计算、保存超时 | 阻断；不输出正式 Word |
| `ScoreValueInvalid` | 公式结果为空、非有限数、Excel 错误 | 阻断并列出分数 ID 和格子 |
| `ReportFieldUnmapped` | Word 中有未识别标记 | 阻断并指明 Word 位置 |
| `ReportRenderFailed` | DOCX 无法保存或版式结构损坏 | 阻断，保留可排查的记录 |
| `ReviewNotApproved` | 业务规则、映射未完成审批 | 只允许明确标注的工程预览，禁止正式发布 |

## 7. 测试计划：必须增加可自动执行的完整矩阵

### 7.1 测试分层

- **T1 静态/单元测试**：Python 层字段映射、JSON 配置、文档结构、公式计划、错误分支，不需要真实 Excel。
- **T2 三文档合成集成测试**：构造可控 PDF、XLSX、DOCX，串通 MD→公式计划→插公式→映射→生成应用的工程链；mock Excel 的结果必须标注 `test_double`。
- **T3 Windows 原生 Excel 测试**：真实 `Excel.Application` 打开安全副本重算，校验缓存结果与独立期望；保存 Excel 版本及输入/输出证据。
- **T4 Word 结构与视觉测试**：DocxTemplate 真实渲染、重新打开、页眉页脚/表格/样式检查；必要时渲染每页供人工对照。
- **T5 EXE 打包及隔离测试**：在不包含 AutoTesting/Gamma 源码的独立目录运行 onedir 包，上传真实填写的 `.xlsx`，产出 Word；记录实际 Windows/Excel 版本、进程返回状态和哈希。
- **T6 真实业务验收**：至少选一套真实 PDF/Excel/Word（推荐先泊车）验证全链；业务疑义应明确列为待审，不允许凭工程样例覆盖真实规则。

### 7.2 最低自动化测试矩阵

| ID | 场景 | 预期结果 |
|---|---|---|
| PDF-01 | 纯文字规程且有评分表 | 生成含评分条款的 MD、JSON 与来源页码 |
| PDF-02 | PDF 跨页表、脚注与单位 | 不丢边界/单位；无法恢复部分标记待审 |
| PDF-03 | 扫描 PDF/主要页面为图片 | 触发 OCR 或明确 `extraction_blocked` |
| PDF-04 | PDF 中存在不确定阈值/矛盾条款 | `pending_review`；不自动形成最终公式 |
| XLS-01 | 分项得分格全空、原表只有合计 SUM 公式 | 能识别并提出分项公式，保留既有汇总 |
| XLS-02 | 一部分已有正确公式 | 不改现有正确公式，仅补充目标空白格 |
| XLS-03 | 得分格已有手工数字 | 默认不覆盖；要求显式批准与差异证据 |
| XLS-04 | 空白目标格没有 OOXML `<c>` 节点 | 能安全处理或阻断并给明确原因 |
| XLS-05 | 得分目标是合并单元格非左上角 | 阻断 |
| XLS-06 | 单元格受保护 | 阻断或按显式受审权限处理 |
| XLS-07 | 拥有格式/下拉框/图表/打印设置 | 公式写入后非目标重要内容保持不变 |
| XLS-08 | 公式循环引用或引用丢失的工作表 | 拒绝写入 |
| XLS-09 | `0`、空白、`否`、无效文本输入 | 按规则区分，不自动混淆 |
| XLS-10 | 边界值、权重、封顶、特殊例外 | 原生 Excel 分数满足人工独立期望 |
| XLS-11 | 公式写入失败 | 原件保留；备份和回滚结果有证据 |
| XLS-12 | Excel COM 不可用 | 真实门禁失败，不能以模拟输出通过 |
| DOC-01 | `{{}}` 在普通段落 | 正确命名和替换 |
| DOC-02 | `{{ }}` 在表格中 | 正确替换且表格结构保持 |
| DOC-03 | 标记横跨多个 Word Run | 不丢标记、文字或格式 |
| DOC-04 | 同一输出分数填多个标记 | 所有位置填相同的本次 Excel 得分 |
| DOC-05 | 页眉页脚中的标记 | 能发现、映射和替换 |
| DOC-06 | 存在未知标记或没有来源的占位符 | 阻断正式报告，不留静默空值 |
| DOC-07 | 完全没有 `{{}}` 的 Word | 按当前模板约束拒绝输入 |
| DOC-08 | 修改后 Word 版式/图片/页码 | 结构校验与视觉检查通过 |
| RUN-01 | **上传真实人工填写的配套 Excel** | **使用上传文件自身得分，报告准确生成** |
| RUN-02 | 上传文件与空白标准模板哈希不同但只有人工输入变化 | **允许通过** |
| RUN-03 | 上传 Excel 中分项公式被改成固定数字 | 阻断并提示具体单元格 |
| RUN-04 | 修改关键中间公式但最终输出公式文本未变 | 校验依赖链或明确阻断风险 |
| RUN-05 | 上传 Excel 的输入修改使得分发生变化 | 输出报告随该变化正确改变 |
| RUN-06 | 两份不同表现的 Excel 依次/批量导入 | 两份 Word 使用各自分数，不交叉/残留 |
| RUN-07 | 缺少某个必填表现格 | 不伪造有效得分；按审核的缺失策略报错 |
| RUN-08 | 得分公式返回 Excel 错误 | 不生成正式报告 |
| RUN-09 | 原生重算失败/Excel 未安装 | 明确失败，不回退 Python 算分 |
| RUN-10 | 上传的用户原文件前后哈希对比 | 完全相等；全部重算发生在副本 |
| RUN-11 | Word 中多个字段需同一 Excel 汇总 | 同一冻结映射，源自本次 Excel |
| RUN-12 | 表格重排/工作表改名/错误模板 | 兼容性检查失败，不误填 Word |
| RUN-13 | 分数为 0 | 视为合法零分（若规则允许），不是空值 |
| RUN-14 | Excel 数字格式为百分比/小数/日期 | Word 值语义和格式正确 |
| RUN-15 | Word 渲染中途抛异常 | 不发布半成品，上传原件安全 |
| RUN-16 | 多次执行输出目录已存在 | 不覆盖先前正式报告，自动唯一编号 |
| REL-01 | 仅构造 mock 的 Excel 成功记录 | 不可标记 Windows-native 已通过 |
| REL-02 | 测试文件 skip 或缺少真实案例 | 不可标记完整业务验证 |

| REL-06 | EXE 拷贝完整分发目录到新位置 | 可正常启动并完成填写 Excel→Word |

### 7.3 特别重要的防伪测试（必须写）

为了证明程序不是偷偷拿内置 Excel 重新计分：

1. 从带公式评分模板复制两份 `A.xlsx`、`B.xlsx`。
2. 在**允许填写的事实格**分别输入两组明确不同、且按评分规程应产生不同结果的数据。
3. 用 Microsoft Excel 分别重算并保存，记录预期得分和文件 SHA-256。
4. 使用同一个 EXE 分别上传 `A.xlsx` 和 `B.xlsx`，断言它们生成的 Word 对应字段有**正确的不同得分**。
5. 运行后再对比 `A.xlsx` 和 `B.xlsx` 原件 SHA-256，必须不变。
6. 在另一个副本中故意把**关键公式格**改成与输入不相关的固定数，必须被程序识别为非法，而不是照样出“正式报告”。
7. 针对一个**不影响映射格式、仅修改已允许输入格**的工作簿，确保哈希不同不会被错误拒绝。

这个测试是本项目最关键的端到端验收标准。没有它，不能宣称已达到用户需求。

### 7.4 真实业务样例顺序

推荐先使用 AutoTesting 中的**智能泊车**资料复制件建立最小真实闭环，再考虑智能安全、智能行车；原因是原仓库已有较多泊车计算及报告验证记录。注意这些样例先前**仍有业务疑义和未映射字段**，因此工程改造可以先将待审字段显式阻断；不要为了通过测试而编造其缺失试验事实或把历史输出标记为正确。

**真实项目的合格交付必须记录具体范围**：哪个 PDF、哪个 Excel、哪个 Word，多少评分项、多少公式目标、多少已映射 Word 位置、哪些通过业务审核、哪些仍待审。不能用“某 54 个结果正确”直接宣布整份原始报告/规程全部正确。

## 9. 审核/审批体系：不能为“自动化”牺牲真实性

### 9.1 必须审查的四类业务对象

1. **评分规则解释**：条款真正表达什么意思，单位、阈值、例外和裁决。
2. **Excel 映射与公式**：输入在哪里、公式输出在哪里、公式是否忠实实现批准规则。
3. **报告字段映射**：每个 Word `{{}}` 对应哪个 Excel 分数或真实元数据，含多次出现的处理。
4. **计算权威与发布**：使用哪个 Microsoft Excel 原生环境测试，哪些真实性证据支持发布。

每类审核对象至少具备：`item_id`、源文件 hash、对象内容 hash、当前状态、审查人、审查时间、理由/证据、影响范围、变更后审批失效规则。

### 9.2 AI 的职责边界

**可以做：** 解析文本、理解条款、提出规则候选、生成公式提案、推荐单元格位置、标出不确定项、生成 MD/JSON 和测试用例、自动校验结构一致性。

**不可以做：** 未确认情况下捏造规程、默认阈值、制造试验事实、自动宣告业务规则已通过、以自身公式计算出的分数证明自身公式正确、凭字段名称自动把历史得分映射为“无碰撞/已完成/合格”。

### 9.3 审核不应变成每一步都无意义地打断用户

- 对证据充分、无歧义、风险较低的候选可以形成合并审核清单，由业务人员集中确认。
- 对影响最终得分或报告结论、存在两个合理解释的关键条款，必须列出选项及其具体分数差异（如可计算）供确认。
- 未审批对象可继续生成工程草稿、标记 `pending`，**但不能进入 business_validated 和正式交付**。
- 用户明确指定“不做业务审批，只要工程验证”时，交付物应带醒目工程非正式标记。

## 10. 安全、稳健性和运行性能要求

### 10.1 文件安全与隐私

- 仅接受支持的扩展名与实质格式，验证 ZIP/OXML 完整性，限制异常超大文件、极端解压比和过量工作表/单元格。
- 拒绝/警示 Excel 宏、ActiveX、外部链接、数据连接、嵌入对象、动态查询和无法安全保存的高级特性。不能直接使用未知用户文件的自动执行能力。
- 绝不执行从 PDF、Excel、Word 中“读出来的指令文本”；这些文件是业务数据，不是程序执行指令。
- 所有中间产物使用独立随机工作目录，防止同名覆盖；对用户原文件采用只读读取/先复制后处理。
- 避免将输入路径中的敏感用户名、测试编号、车辆身份或试验事实全文放入普通日志；报告审计可以保存所需字段，但应受控。
- 不在运行时联网上传用户文件；除非未来需求明确提出，并另行取得许可。

### 10.2 Excel COM 健壮性

- 120 秒等固定超时时间应对实际复杂工作簿可配置并有可靠失败处理；不同大小不能一刀切“等待不足就假定成功”。
- 记录打开、重算、保存、关闭每一步状态。
- 避免 Excel 进程异常遗留、后台弹窗或等待外链导致卡死；保证失败后 Word 不出正式成品。
- Windows 非英语地区 Excel 环境下，使用规范公式与安全的数据类型转换。
- 批量多个 Excel 默认串行运行，防止 Excel COM 竞争导致文件混淆。

### 10.3 异常提示与可观测性

- 对用户：展示“哪个文件、哪个工作表/单元格、缺什么条件、怎么处理”，不要只打印 Python 堆栈。
- 对开发人员：在审计/诊断日志记录结构化错误码和受控堆栈。
- 每次构建和日常运行应生成自己的运行 ID、时间戳和版本信息；可从 Word 结果反查到实际输入工作簿 hash。

### 10.4 兼容现有 Gamma

- 先保留现有人工审核、`engineering_sample` 水印、字段审查对话框、源码与资源隔离等正确设计。
- 尽量向后兼容旧 `autotesting-project-v1` 和 `run_job_from_facts()`，但不能让向后兼容限制新用户场景。需要迁移时提供真实迁移测试与说明。
- Gamma 现有 `vendor/VENDOR.md` 标记了冻结的上游组件；如改 vendor 文件，必须更新来源、hash、差异和对应测试，不可悄悄修改冻结副本并声称与上游完全一致。

## 附录 A：用户最终操作流程（用于写帮助文档和 UI 提示）

**首次准备（由 Skill/Codex/业务审核人员完成一次）**：

1. 选中评分规程 PDF、原始评分 Excel 和空白 Word 模板。
2. AI 形成 `评分细则.md`、逐条来源、关键歧义与评分项清单。
3. 校对 Excel 单元格映射和公式计划，完成业务规则确认。
4. 生成并验证带评分公式的 Excel；检查输入格、得分格和汇总公式。
5. 映射所有 Word `{{}}` 到具体得分或真实元数据，确认字段。
6. 生成专属 Windows 程序和必要的内部配置；执行真实测试并交付。

**以后每次测试（由普通测评人员完成）**：

1. 打开交付的带公式 Excel 评分模板副本。
2. 在指定试验表现/人工判定格填入真实数据，保存；不修改得分公式。
3. 双击应用目录中的 EXE（目标电脑须满足 Excel 环境要求）。
4. 选择这份已填写的 `.xlsx`，选输出文件夹，点击“生成检验报告”。
5. 程序核对文件版本、公式/结构、重算得分并填 Word；用户打开结果检查。
6. 对报错按具体单元格提示修正输入或使用正确模板，不要通过人为覆盖得分格来规避报错。

## 附录 B：反模式清单（代码评审直接检查）

出现下列情况应退回修改：

- EXE “支持 Excel 上传”，但内部仍只有 `load_facts_from_excel()` + `run_job_from_facts()`，并无直接基于上传工作簿的服务入口。
- Word 分数取自程序自带的空白模板或历史已缓存结果，而不是本次上传 Excel 的计算结果。
- 上传 Excel 因 hash 和交付的空白评分 Excel 不一致而失败，即使用户只改变了合法表现格。
- 在 Python 中写了一份与 PDF 规则等价的评分 `if/else` 作为 Excel 不可用时的后备结果。
- PDF 只输出原文 JSON，没有 `评分细则.md`、来源页码和条款审核。
- 公式写入仅生成 JSON 计划，实际 Excel 得分单元格仍然空白或固定值。
- 只测试合成的 `=IF(A2<=10,2,0)`，却据此宣称所有真实业务规程都正确。
- 把 AutoTesting 旧 IVISTA Python RulePack/评分器原样塞入运行 EXE。
- `{{}}` 只按遍历顺序替换，不保留上下文来源、位置 ID 或语义审核。
- 文档中宣称 EXE 可脱离 Excel 安装运行，但实现仍使用 Microsoft Excel COM。
- PyInstaller 产出 onedir，却只交付里面的单个 EXE，没有 `_internal` 等依赖资源。
- 仅因为测试文件存在、pytest skipped、mock Excel 回报 passed 就宣布真实验收成功。
- “所有业务审核通过”仅靠更改 `release_status` 或 `delivery-manifest.json` 字符串，而没有有名、有来源的实际审批与校验。
- 为了让测试通过而编造测试数据、填补 Word 缺失事实、假设没有证据的“已碰撞/未碰撞/通过”。
- 自动删除/覆盖 AutoTesting 用户下载的真实原始文档或 Gamma 用户未提交的修改。
